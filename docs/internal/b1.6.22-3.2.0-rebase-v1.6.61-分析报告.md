## 1. 执行摘要

| 维度 | 数值 | 说明 |
|------|------|------|
| 版本跨度 | **v1.6.22 → v1.6.61** | 官方开源版本相差 **39 个小版本**（v1.6.23–v1.6.61） |
| 上游提交数 | **490 commits** | 自 v1.6.22 以来开源主线变更 |
| 定制提交数 | **41 commits** | b1.6.22-3.2.0 相对 v1.6.22 的定制开发 |
| 上游代码变更 | **2341 文件**，+257,408 / -31,591 行 | 体量极大，Rust 与文档占主导 |
| 定制代码变更 | **67 文件**，+7,381 / -3,220 行 | 集中在指标引擎、国产数据库、CI/镜像 |
| 双方改动重叠文件 | **24 个** | 潜在冲突热点 |
| 一次性 merge 硬冲突 | **8 个文件** | 6 个 modify/delete + 2 个 content |
| Rebase 预估冲突轮次 | **约 3–5 轮** | 实测模拟（见 §5） |

**结论**：版本差距非常大（约 5 个月、490 个上游提交），但定制改动相对集中（67 文件）。Rebase **可行但工作量大**，核心风险在 **schema-compiler 指标逻辑** 与 **Rust 目录重构**，而非 Git 冲突数量本身。

## 7. 推荐升级策略

### 方案 A：Rebase（推荐用于保持线性历史）

```bash
git checkout b1.6.22-3.2.0
git rebase --onto v1.6.61 tags/v1.6.22
```

- **预估工作量**：2–5 人天（冲突解决 0.5 天 + 回归测试 2–4 天）
- **冲突处理**：约 3–5 轮，8 个文件需关注
- **优点**：历史清晰，后续跟进上游方便
- **缺点**：需逐个提交处理冲突

### 方案 B：Merge（推荐用于快速集成分支）

```bash
git checkout b1.6.22-3.2.0
git merge v1.6.61
```

- **预估工作量**：1–3 人天
- **冲突**：与 rebase 相同 8 个文件，但只需处理一次
- **优点**：一次性解决冲突，操作简单
- **缺点**：产生 merge commit，历史非线性

### 方案 C：Cherry-pick 定制提交到新分支（推荐用于彻底重构）

```bash
git checkout -b b1.6.61-gienbi v1.6.61
# 按功能模块 cherry-pick 或手动移植
```

- **预估工作量**：5–10 人天
- **优点**：可借机清理早期 CI/workflow 提交，按模块整理
- **缺点**：工作量大，需逐功能验证

### 无论哪种方案，必须执行的验证

```bash
# 1. 编译
yarn install && yarn tsc

# 2. schema-compiler 单元测试（核心）
cd packages/cubejs-schema-compiler && yarn test

# 3. 定制测试
yarn test --testPathPattern="semi-additive|dm-query|credit-loan"

# 4. DM 驱动
cd packages/cubejs-dm-driver && yarn test  # 如有

# 5. 冒烟：时点指标 + 同环比 + 达梦数据源查询
```

## 8. 关键注意事项

### 8.1 Rust 路径迁移（#10784）

定制分支修改了旧路径：

```
rust/cubesqlplanner/cubesqlplanner/src/planner/planners/multi_stage/member_query_planner.rs
rust/cubesqlplanner/cubesqlplanner/src/logical_plan/multistage/get_date_range.rs
rust/cubesqlplanner/cubesqlplanner/src/physical_plan_builder/processors/multi_stage_get_date_range.rs
```

上游 v1.6.40 将其移至：

```
rust/cube/cubesqlplanner/cubesqlplanner/src/planner/planners/multi_stage/member_query_planner.rs
rust/cube/cubesqlplanner/cubesqlplanner/src/logical_plan/multistage/get_date_range.rs
rust/cube/cubesqlplanner/cubesqlplanner/src/physical_plan_builder/processors/multi_stage_get_date_range.rs
```

Rebase 后旧路径下的文件将不存在，**必须手动将定制逻辑移植到新路径**。

### 8.2 Tesseract 与 JS 规划器双轨

v1.6.61 默认启用 Tesseract 原生规划器（`CUBESQL_SQL_PUSH_DOWN`）。定制分支的时点/半累加逻辑主要在 JS `BaseQuery.js` 中实现。需确认：

- Tesseract 开启时，定制逻辑是否仍走 JS 路径
- 多阶段 CTE 栈溢出修复（`8fbb4c2e`）在 Tesseract 下是否仍需要

### 8.3 被跳过的提交需人工确认

| 提交 | 功能 | 行动 |
|------|------|------|
| `da64f5ea` 删除 schema 文件接口 | API 扩展 | 确认 `gateway.ts` 中是否已包含 |
| `3a7e7eb55e` OWXJ-743 期间累计筛选 | 指标 bug 修复 | 确认 `BaseQuery.js` 最终版本是否包含修复 |

### 8.4 Husky 钩子问题

本地 rebase 时 `.git/hooks/husky.local.sh` 引用了 `packages/cubejs-dm-driver/`，在 rebase 中间状态会报错（目录尚未创建）。建议 rebase 时临时设置 `HUSKY=0`。
