### 4.1 冲突分级说明

| 级别 | 含义 | 处理策略 |
|------|------|---------|
| 🔴 P0 硬冲突 | Git 无法自动合并，必须手工解决 | 逐行合并，保留双方有效逻辑 |
| 🟡 P1 自动合并 | Git 可合并，但双方均改动同一逻辑 | 合并后必须跑对应测试 |
| 🟢 P2 无冲突 | 仅定制或仅上游改动 | 直接保留，冒烟验证即可 |

## 六、升级操作建议

### 6.1 推荐流程

```
1. 创建备份分支
   git branch b1.6.22-3.2.0-backup b1.6.22-3.2.0

2. Rebase（或 merge）
   HUSKY=0 git rebase --onto v1.6.61 tags/v1.6.22

3. 按 §4 解决冲突
   - P0：workflows 删除、package.json、Rust 路径移植
   - P1：BaseQuery.js 等自动合并文件人工 review

4. 编译验证
   yarn install && yarn tsc

5. 按 §5 执行回归测试
   - 先跑单元测试
   - 再跑 OWXJ 业务用例
   - 最后 Tesseract 开启场景

6. 构建镜像并发版
   触发 publish.yml 或本地 docker build
```

### 6.2 工作量预估

| 阶段 | 预估时间 |
|------|---------|
| Git 冲突解决 | 0.5–1 天 |
| Rust 路径移植 | 0.5 天 |
| 单元测试修复 | 0.5 天 |
| OWXJ 业务回归 | 1–2 天 |
| 数据库驱动冒烟 | 0.5 天 |
| Docker 镜像验证 | 0.5 天 |
| **合计** | **3–5 人天** |

### 6.3 注意事项

1. **Husky 钩子**：rebase 过程中 `packages/cubejs-dm-driver/` 可能尚未创建，设置 `HUSKY=0` 跳过
2. **Rust 旧路径**：rebase 后检查是否残留 `rust/cubesqlplanner/` 目录，定制逻辑应在 `rust/cube/cubesqlplanner/`
3. **Tesseract 默认开启**：v1.6.50 起强制 native orchestrator，必须验证时点指标在 Tesseract 路径下的行为
4. **跳过的提交**：rebase 后对比 §4.4 确认功能未丢失
5. **yarn.lock**：冲突时优先采用上游 lock，再 `yarn install` 重新解析
